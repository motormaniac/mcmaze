# General Notes
Center and corner are static reference points that may exist in the world (they are not killed between loops)
Path and maze are killed between loops, so they should be resummoned
All repeating command block (all loops) should be self terminating: all loops must terminate themselves based on an external event, such as detecting if maze or path have been killed.

# General Description of the whole process
1. Summon an armor stand named center
2. Based on the .global x and y scores, create an armor stand named corner and place it in the corner cell of the maze.
3. Create two borders for each of the two levels.
  - When generating borders, path first goes straight towards north
  - Borders are a square ring of netherite blocks that hug the outside of the maze bounds. These blocks DO NOT fall within the designated cell areas, but rather hug the outer perimeter.
  - The netherite blocks mark a closed wall
  - The spiral algorithm turns if there is an emerald block in the cell in front of it.
    Thus, in the outer ring of cells, at each corner cell, an emerald block is placed in the cell IN FRONT.
    Since it is placed in front, this emerald block IS NOT within the maze cell bounds. It is one cell outside.
4. An armor stand named maze will place multiblock rooms in random locations of the map
  a. First summon maze at corner
  b. Choose random x and z cell coordinates within the range of .global x and z scores.
  c. The armor stand moves to that random position, then attempts to place a multiblock. Attempts only succeed if the multiblock fits within the space provided and if it matches adjacent walls.
  d. After 5 failed attempts, a new random position is picked
  e. After a certain percentage of the map is filled, the multiblock stops.
5. Place multiblock for second level
6. For first level, summon an armor armor stand named path at corner, then run the path algorithm.
  a. The path moves in a clockwise inward spiral, where path first moves straight towards north.
  b. Whenever the cell in front of path is occupied (denoted by the emerald block at ~ ~-100 ~), path turns to its right, then continues moving forward.
  c. If after turning path finds another occupied cell in front, that means it has completed the spiral.
  d. Path moves in increments of 7 blocks (the cell size)
  e. At each step, path marks its cell as occupied (with an emerald block)
7. At each step of the path pattern, a separate armor stand named maze at path's position generates the room.
  a. If there is any obstruction at all within the cell space, do not generate a room. (This accounts for preplaced structures)
  b. First, check and match the walls of adjacent rooms.
  c. Randomly pick the rest of the missing walls based on these rules:
    - If two walls are already closed, pick between an open or a hidden to prevent dead ends.
    - If one or less walls are closed (at least three open), then pick between open, hidden, or closed
    - Activate the redstone encoder to find the corresponding maze room, and spawn it at maze.

# Forceload
-- similar to clear, forceloads start at origin's corner, then expand out in the x and z directions.
-- One x armor stand shoots right, spawning a z armor stand every step that shoots forward.
-- The chunk that origin resides in is UNAFFECTED by this process, since origin handles its own chunk separately.
-- The same logic is used for forceload add or forceload remove; it is controlled by either the add or remove tag on all the load armor_stands
-- It takes one tick for the forceload commands to take affect; ex: add won't load the chunk until next tick, and remove won't remove the chunk until next tick

## Init add
execute as @n[type=armor_stand,name=origin] at @s run summon armor_stand ~ ~ ~ {CustomName:xload,CustomNameVisible:1b,NoGravity:1b,Tags:[load,new,add]}
execute as @n[type=armor_stand,name=origin] at @s run summon armor_stand ~ ~ ~ {CustomName:zload,CustomNameVisible:1b,NoGravity:1b,Tags:[load,new,add]}
{start loop}

## Init remove
execute as @n[type=armor_stand,name=origin] at @s run summon armor_stand ~ ~ ~ {CustomName:xload,CustomNameVisible:1b,NoGravity:1b,Tags:[load,new,remove]}
execute as @n[type=armor_stand,name=origin] at @s run summon armor_stand ~ ~ ~ {CustomName:zload,CustomNameVisible:1b,NoGravity:1b,Tags:[load,new,remove]}
{start load}

-- Loop mechanics:
(the same behavior applies for x and z)
Forceload adding:
forceload the chunk in front before teleporting into it
x=3  #the total width of chunk cells ex: the total area being loaded is 3x3 chunks
The armor stand starts in the start cell. It forceload adds the next chunk, then moves into the next chunk.
Note that the armor stand DOES NOT load the chunk it starts in, and it doesn't teleport off the grid where it can't be loaded.
x =    3    2  1  0
Move:     >  >
    [start][A][A]
Forceload removing:
Forceload the current chunk then teleport into the next chunk.
Remove has the same movement pattern as add, except the moments when it removes is shifted. Remove does not trigger on the first cell, and it is also active while x >= 1 instead of >= 2.
x =  3  2  1
Move:      >  >
    [start][R][R]
For some reason, you have to wait an additional cycle before killing all the entities. Kill when x = 0

# RANDOM ROOMS (Multiblocks and stairs)
## Explaining random weights of Multiblocks
Each level has a fill level percentage for multiblocks. Ex: in a 10x10 with a fill level percent of 40%, the multiblockFill amount is 10*10*40% = 40 multiblock cells allocated
As multiblocks are placed, mutliblockFill is reduced until it reaches 0. multiblockFill 0 means that level is done.
Since empty percentage is included in per level multiblockFill, random chance percentages are recalculated to include ONLY the non empty things.
  Ex: 25% empty, 50% 1 high, 25% 2 high --> 66% 1 high, 34% 2 high
The empty percentage is subtracted from the fill level using another percentage. Ex: 20% empty --> multiblockFill *= 80%
Also note that both staircases and 2 high multiblocks are both considered 2 high
1 level: all multiblocks are 1 level (100% 1 high multi)
2 levels:
  - the bottom level is 50% filled with 2 highs and 50% filled with 1 high
    - emptyFill 100%
    - 17% stair, 17% 2 high multi, 17% 2 high open sky, 49% 1 high
  - the top level is already 50% empty (from the 2 highs in level 1), so it only needs to fill 50% 1 high
    - emptyFill 50%
    - 100% 1 high
3 or more levels:
  - bottom level = 34% 2 high, 66% 1 high
    - emptyFill 100%
    - 17% stair, 17% 2 high, 66% 1 high
  - middle level(s) = 33% (empty, already occupied from below level), 34% 2 high, 33% 1 high
    - emptyFill 66%
    - 25% stair, 25% 2 high multi, 50% 1 high multi
  - second to last level = 33% (empty, already occupied from below level), 34% 2 high, 33% 1 high
    - emptyFill 66%
    - 17% stair, 17% 2 high, 17% 2 high open, 49% 1 high
  - top level = 34% (empty, already occupied), 66% 1 high
    - emptyFill 66%
    - 100% 1 high
